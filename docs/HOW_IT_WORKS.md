# Gym Management System အလုပ်လုပ်ပုံ

ဒီစာရွက်မှာ နည်းပညာစကားလုံးတွေကို တတ်နိုင်သလောက်မသုံးဘဲ၊ Gym မှာ နေ့စဉ်ဘယ်လိုအသုံးပြုမလဲဆိုတာ ရိုးရိုးရှင်းရှင်း ရှင်းပြထားပါတယ်။

> ဒီစာရွက်က တည်ဆောက်မည့်စနစ်တစ်ခုလုံးရဲ့ ရည်မှန်းပုံကို ရှင်းပြတာဖြစ်ပါတယ်။ လက်ရှိတကယ်ပြီးစီးနေမှုကို [`DEVELOPMENT_PLAN.md`](./DEVELOPMENT_PLAN.md) ရဲ့ phase exit criteria နဲ့ စစ်ရပါမယ်။ စာရွက်ထဲပါရုံနဲ့ လုပ်ဆောင်ချက်ပြီးပြီလို့ မဆိုလိုပါ။

> စာရွက်စာတမ်းအားလုံးရဲ့ အညွှန်းကို [`README.md`](./README.md) မှာကြည့်ပါ။ ဒီစာရွက်က နည်းပညာစာရွက်တွေမှာ သတ်မှတ်ထားတဲ့ စည်းမျဉ်းတွေကို ရိုးရှင်းစွာ ပြန်ရှင်းပြတာဖြစ်ပါတယ် — အသေးစိတ်ကို [`ARCHITECTURE.md`](./ARCHITECTURE.md)၊ [`DATABASE.md`](./DATABASE.md)၊ [`API.md`](./API.md)၊ [`SECURITY.md`](./SECURITY.md) မှာ ကြည့်ပါ။ ကွဲလွဲမှုရှိရင် အဲဒီစာရွက်တွေက အတည်ဖြစ်ပါတယ်။

---

## အရင်ဆုံး သိထားရမည့်အချက်

ဒီစနစ်က Member၊ Trainer/PT၊ Class၊ Staff Management၊ Membership/Renewal၊ Payment၊ Attendance၊ Product/Inventory နဲ့ Reports အားလုံးကို တစ်နေရာတည်းမှာ စီမံနိုင်ရပါမယ်။

Gym တစ်ဆိုင်ချင်းစီကို သီးခြားဆိုင်တစ်ခုအဖြစ် သတ်မှတ်ပါတယ်။ Member၊ Staff၊ Trainer၊ Class၊ Payment၊ Attendance၊ Product၊ Stock၊ Notification နဲ့ Report အားလုံးမှာ သက်ဆိုင်ရာ Gym ကို Server က သတ်မှတ်ပေးပြီး အခြား Gym ရဲ့ စာရင်းကို ကြည့်၊ ပြင်၊ ချိတ်ဆက်၊ ရေတွက် သို့မဟုတ် Report ထဲရောထည့်လို့ လုံးဝမရပါ။ Gym အများကို စီမံခွင့်ရှိတဲ့ Account ဖြစ်ရင်လည်း Login ဝင်ပြီးနောက် Gym တစ်ခုကို ရွေးပြီး အဲဒီ Gym ရဲ့အချက်အလက်ကိုသာ တစ်ကြိမ်မှာ အသုံးပြုရပါမယ်။

အဓိကမှတ်တမ်းတွေက —

- **Member** — ဒီလူက ဘယ်သူလဲ
- **Membership** — ဘယ်ပလန်ကို ဘယ်နေ့အထိ ဝယ်ထားလဲ
- **Check-in / Check-out** — ဒီနေ့ ဘယ်အချိန်ဝင်ပြီး ဘယ်အချိန်ထွက်လဲ
- **Payment / Receipt** — ငွေဘယ်လောက်ပေးပြီးလဲ
- **Trainer / PT / Class** — ဘယ် Trainer နဲ့ ဘယ်အချိန်လေ့ကျင့်မလဲ၊ Session ဘယ်နှစ်ကြိမ်ကျန်လဲ
- **Product / Inventory** — ဖျော်ရည်၊ ရေ၊ fitness ပစ္စည်း စတဲ့ Item တွေ ဘယ်လောက်ရှိပြီး ဘယ်လောက်ရောင်းရလဲ
- **Report / Dashboard** — Member၊ Attendance၊ Income၊ Expense၊ Product နဲ့ Profit အခြေအနေ

Member မှတ်တမ်းရှိရုံနဲ့ Gym ဝင်လို့မရသေးပါ။ သက်တမ်းရှိပြီး ငွေရှင်းပြီးသား Membership လည်းရှိရပါမယ်။

> **ငွေကြေးအကြောင်း** — ဒီစာရွက်ထဲက ငွေပမာဏ ဥပမာအားလုံး (ဥပမာ `100,000`) က Gym တစ်ဆိုင်ချင်းစီရဲ့ သတ်မှတ်ငွေကြေးဖြင့်ဖြစ်ပါတယ်။ Gym အသစ်တစ်ဆိုင်ရဲ့ စတင်သတ်မှတ်ချက်က ထိုင်းဘတ် (`THB`) ဖြစ်ပါတယ်။ မှတ်တမ်းတစ်ခုချင်းစီမှာ ငွေကြေးကုဒ်ကို သိမ်းပြီး တစ်ခုတည်းသောစာရင်းထဲ ငွေကြေးအမျိုးအစား နှစ်မျိုးရော၍မထည့်ပါ။

## ဘယ်သူက ဘာလုပ်မလဲ

### Reception

- Member အသစ်အပ်ပေးမယ်
- Membership ပလန်ရွေးပေးမယ်
- Payment၊ Expense၊ PT Sale နဲ့ Salary ကို **Draft စာရင်းပြင်ဆင်**ပြီး **Submit တင်ပြ**မယ်
- Member ကို Check-in / Check-out လုပ်ပေးမယ်
- မိမိ Reception Account နဲ့ ကိုယ်တိုင်ဖွင့်ထားတဲ့ Cash Session ကိုသာ ကြည့်၊ ကောင်တာလုပ်ငန်းအတွက် အသုံးပြု၊ စာရင်းညှိပြီး ပိတ်မယ်
- ငွေစာရင်းကို Approve/Post မလုပ်ရသလို Cash ကို လက်ဖြင့် Adjustment မလုပ်ရပါ

### Manager

- Reception သို့မဟုတ် အခြားဝန်ထမ်းတင်ထားတဲ့ ငွေစာရင်းတွေကို စစ်မယ်
- မှန်ရင် Approve လုပ်မယ်
- မှားရင် အကြောင်းရင်းရေးပြီး Reject လုပ်မယ်

ဒီနေရာမှာ လုပ်ငန်း ၄ မျိုးကို ခွဲထားပါတယ် —

1. **Operation** — Reception က မိမိဖွင့်ထားတဲ့ Cash Session ကို ကောင်တာမှာ အသုံးပြုခြင်း
2. **Preparation** — Payment/Expense/PT Sale/Salary Draft ကို ရေး၊ ပြင်၊ Submit လုပ်ခြင်း
3. **Approval** — သီးခြား Manager/Owner က Submitted Draft ကို စစ်ပြီး Approve/Reject လုပ်ခြင်း
4. **Posting** — Approve ပြီးမှ System က Payment၊ Receipt၊ Expense နဲ့ Cash Movement ကို အတည်မှတ်တမ်းအဖြစ် တစ်ပြိုင်နက်ရေးခြင်း

Reception က Operation နဲ့ Preparation ပဲလုပ်နိုင်ပြီး Approval နဲ့ Posting အခွင့်အာဏာ မရှိပါ။

### Owner

- Gym တစ်ခုမှာ Owner တစ်ယောက်ထက်ပိုပြီး သီးခြား Account နဲ့ Login ဝင်နိုင်မယ်
- Manager လို Approve / Reject လုပ်နိုင်မယ်
- Gym ရဲ့ ဝင်ငွေ၊ ကုန်ကျစရိတ်နဲ့ အမြတ်ကို Dashboard မှာ ကြည့်မယ်
- ဝန်ထမ်းနဲ့ System Settings တွေကို စီမံမယ်

Owner အသစ်ထည့်ခြင်းနဲ့ ဖယ်ခြင်းကို Owner ကသာလုပ်နိုင်မယ်။ Gym တစ်ခုမှာ Owner အနည်းဆုံးတစ်ယောက် အမြဲကျန်ရမယ်။ လက်ရှိအဆင့်မှာ Owner တိုင်းက အခွင့်အရေးတူပြီး ရှယ်ယာရာခိုင်နှုန်းနဲ့ အမြတ်ခွဲဝေမှုကို မတွက်သေးပါ။ နောက်ပိုင်းလိုအပ်ရင် သီးခြားစနစ်အဖြစ် ထပ်တိုးနိုင်ပါတယ်။

### Accountant

- Payment၊ Expense နဲ့ Salary စာရင်းရေးနိုင်မယ်
- နေ့ချုပ်စာရင်းနဲ့ Report တွေကို စစ်မယ်
- ကိုယ်တိုင် Approve မလုပ်ရပါ

### Trainer

- မိမိတာဝန်ယူထားတဲ့ Member တွေကို ကြည့်မယ်
- မိမိ PT နဲ့ Class အချိန်ဇယားကို ကြည့်မယ်
- တက်ရောက်ပြီး/ပျက်ကွက်/ဖျက်သိမ်းထားတဲ့ Session ကို မှတ်တမ်းတင်မယ်
- PT ရောင်းချမှုနဲ့ မိမိကော်မရှင်ကို ကြည့်မယ်

### Member

- မိမိ Membership သက်တမ်းနဲ့ ငွေရှင်းမှတ်တမ်းကို ဖုန်းကနေကြည့်မယ်
- မိမိ PT/Class အချိန်ဇယားနဲ့ ကျန် Session အရေအတွက်ကို ကြည့်မယ်
- Counter မှာ လူမရှိလည်း Gym ရဲ့ လက်ရှိ QR ကို App နဲ့ဖတ်ပြီး Check-in လုပ်နိုင်မယ်
- Membership reminder၊ Gym event နဲ့ promotion announcement တွေကို App မှာ လက်ခံနိုင်မယ်
- အခြား Member ရဲ့အချက်အလက်ကို မမြင်ရပါ

## နေ့တစ်နေ့ စတင်ပုံ

Reception က အလုပ်စဝင်တဲ့အခါ —

1. System ထဲ Login ဝင်မယ်
2. Gym တစ်ခုတည်းသာရှိရင် ချက်ချင်းဝင်မယ်။ Gym အများရှိရင် ၅ မိနစ်အတွင်း တစ်ခုရွေးရမယ်
3. ငွေသားကောင်တာအတွက် **စတင်ငွေ** ထည့်မယ်
4. Cash Session ဖွင့်မယ်
5. Member တွေကို စတင်လက်ခံမယ်

Cash Session မဖွင့်ထားရင် ငွေသား Payment ကို အတည်ပြုလို့မရပါ။

Reception တစ်ယောက်က မိမိ Account နဲ့ ဖွင့်ထားတဲ့ Session ကိုသာ ကြည့်၊ အသုံးပြု၊ စာရင်းညှိပြီး ပိတ်နိုင်ပါတယ်။ အခြား Reception ဖွင့်ထားတဲ့ Session နဲ့ အခြား Gym ရဲ့ Session ကို မမြင်နိုင်၊ မသုံးနိုင်ပါ။ `opened_by_membership_id` က လက်ရှိ Reception ရဲ့ Gym Membership နဲ့ တူမတူကို Server က စစ်ပါတယ်။

## Member အသစ်တစ်ယောက် အပ်ပုံ

ဥပမာ — ကိုမင်း Gym ကို ပထမဆုံးလာပြီး ၁ လပလန်ဝယ်မယ်။

### အဆင့် ၁ — Member အချက်အလက်ထည့်မယ်

Reception က —

- အမည်
- ဖုန်းနံပါတ်
- အပ်သည့်နေ့
- မွေးနေ့ (ရှိရင်)
- အရေးပေါ်ဆက်သွယ်ရန်
- ဓာတ်ပုံ (ရှိရင်)

တို့ကို ထည့်မယ်။ System က Member ID တစ်ခု ထုတ်ပေးမယ်။

### အဆင့် ၂ — Membership ပလန်ရွေးမယ်

Reception က ၁ လ၊ ၃ လ၊ ၁ နှစ် စတဲ့ပလန်ထဲက တစ်ခုရွေးမယ်။

System က —

- စတင်ရက်
- သက်တမ်းကုန်ရက်
- ပလန်ဈေး
- လျှော့ဈေး
- နောက်ဆုံးပေးရမည့်ငွေ

ကို အလိုအလျောက်တွက်မယ်။

### အဆင့် ၃ — ငွေရှင်းစာရင်းတင်မယ်

Reception က Payment စာရင်းရေးပြီး Manager သို့မဟုတ် Owner ထံတင်မယ်။

ဒီအချိန်မှာ —

- Receipt မထွက်သေးပါ
- Membership ကို ငွေရှင်းပြီးပြီလို့ မသတ်မှတ်သေးပါ
- Cash Book ထဲ ငွေမဝင်သေးပါ

### အဆင့် ၄ — Manager/Owner စစ်မယ်

Manager သို့မဟုတ် Owner က Member၊ ပလန်၊ ငွေပမာဏနဲ့ ငွေပေးချေနည်းကို စစ်မယ်။

မှန်ရင် **Approve** လုပ်မယ်။ အဲဒီအချိန်မှသာ —

- Payment အတည်ဖြစ်မယ်
- Receipt ထွက်မယ်
- Membership ငွေရှင်းပြီးဖြစ်မယ်
- ငွေသားဆိုရင် Cash Book ထဲဝင်မယ်

မှားရင် **Reject** လုပ်မယ်။ Reject လုပ်ထားတဲ့စာရင်းက ဝင်ငွေထဲမပါပါ။

> စာရင်းရေးသူက မိမိစာရင်းကို ကိုယ်တိုင် Approve မလုပ်ရပါ။ သီးခြား Manager သို့မဟုတ် Owner က စစ်ရပါမယ်။

Approve လုပ်ခြင်းက Posting ကို ခွင့်ပြုတာဖြစ်ပြီး Receipt/Cash Movement ကို Reception က ကိုယ်တိုင်ရေးထည့်တာမဟုတ်ပါ။ System က Server ပေါ်မှာ တစ်ပြိုင်နက်အတည်ပြုရေးသွင်းပါတယ်။

Counter မှာ လူမရှိရင် Gym မှာပြထားတဲ့ အချိန်တိုအတွင်းသာသုံးလို့ရသော ပြောင်းလဲနေတဲ့ QR ကို Member သို့မဟုတ် ခွင့်ပြုထားတဲ့ Trainer က Mobile App နဲ့ဖတ်နိုင်ပါတယ်။ App က Login ဝင်ထားသူ၊ ရွေးထားတဲ့ Gym၊ QR သက်တမ်းနဲ့ Check-in eligibility ကို Server ဆီမှာစစ်ပြီးမှ Check-in မှတ်တမ်းရေးပါမယ်။ QR ဓာတ်ပုံဟောင်း၊ ပြန်သုံးထားတဲ့ QR၊ အခြား Gym QR နဲ့ အခြား Member အတွက် Check-in လုပ်ခြင်းကို လက်မခံပါ။ QR ထဲမှာ Member အမည်၊ ဖုန်းနံပါတ် သို့မဟုတ် အမြဲသုံးလို့ရတဲ့ Secret မပါရပါ။

System က အောက်ပါအချက်တွေကို စစ်မယ် —

- Member အသက်ဝင်နေသလား
- Membership ရှိသလား
- ငွေရှင်းပြီးပြီလား
- သက်တမ်းကုန်ပြီးပြီလား
- Check-in နှစ်ခါထပ်လုပ်ထားသလား

အားလုံးမှန်ရင် ဝင်ခွင့်ပေးမယ်။ မမှန်ရင် “သက်တမ်းကုန်နေသည်”၊ “ငွေမရှင်းရသေးပါ” စသဖြင့် အကြောင်းရင်းပြမယ်။

## နောက်နေ့ ပြန်လာရင်

Member အသစ်ပြန်ဖွင့်စရာ မလိုပါ။

1. Member ကို ရှာမယ် သို့မဟုတ် QR ဖတ်မယ်
2. Membership သက်တမ်းကို System က စစ်မယ်
3. သက်တမ်းရှိရင် Check-in လုပ်မယ်
4. Train ပြီးရင် Check-out လုပ်မယ်

သက်တမ်းကုန်ခါနီး ၃၀ ရက်၊ ၇ ရက်၊ ၃ ရက်နဲ့ သက်တမ်းကုန်တဲ့နေ့မှာ သတိပေးနိုင်ပါတယ်။

Member က Email လိပ်စာပေးထားရင် System က Membership သက်တမ်းကုန်တော့မယ့်အကြောင်း Email ပို့မယ်။ Email ထဲမှာ Member အမည်၊ လက်ရှိပလန်နဲ့ သက်တမ်းကုန်မယ့်ရက် ပါမယ်။

Member က Email မပေးထားရင် Email မပို့ပါ။ ဖုန်းနံပါတ်သို့ အလိုအလျောက်ပြောင်းပို့ခြင်းလည်း မလုပ်ပါ။ Email တစ်စောင်တည်းကို ထပ်ခါထပ်ခါ မပို့အောင် System က မှတ်ထားမယ်။

Mobile App အသုံးပြုသူက Push Notification ခွင့်ပြုထားရင် သက်တမ်းကုန်ခါနီး Reminder ကို App Notification အဖြစ်လည်း လက်ခံနိုင်ပါတယ်။ Owner/Manager က Gym event သို့မဟုတ် promotion announcement တစ်ခုရေးပြီး သတ်မှတ်ထားတဲ့ Member အုပ်စုသို့ ပို့နိုင်ပါတယ်။ Announcement တစ်ခုကို အခြား Gym Member ဆီ မပို့ရသလို Member က Notification ပိတ်ထားရင် သူ့ရွေးချယ်မှုကို လေးစားရပါမယ်။

သက်တမ်းတိုးချင်ရင် Membership အသစ်ဖွင့်ပြီး Payment ကို ထပ်တင်ရပါမယ်။

## PT သုံးတဲ့ Member

Member ကို Trainer တာဝန်ပေးထားရင် Member စာရင်းမှာ **PT** ဆိုတဲ့အမှတ်အသားပြမယ်။

- Trainer တာဝန်ရှိနေသရွေ့ PT အမှတ်အသားပြမယ်
- Trainer တာဝန်ပြီးသွားရင် အမှတ်အသားပျောက်မယ်
- ဝန်ထမ်းက PT Yes/No ကို လက်ဖြင့်ပြောင်းစရာမလိုပါ

PT Package သို့မဟုတ် Class Package ဝယ်ထားရင် စုစုပေါင်း Session၊ အသုံးပြုပြီး Session၊ ကျန် Session နဲ့ သက်တမ်းကုန်ရက်ကို System ကတွက်ပေးမယ်။ Booking တစ်ခုမှာ Trainer၊ Member/Class၊ စမည့်/ပြီးမည့်အချိန်နဲ့ အခြေအနေကို မှတ်တမ်းတင်မယ်။ တက်ရောက်ပြီးကြောင်း အတည်ပြုမှ Session ကို နုတ်ပြီး Cancel/No-show မူဝါဒအတိုင်းသာ ပြန်ထည့် သို့မဟုတ် နုတ်မယ်။ Trainer တစ်ယောက်၊ Member တစ်ယောက် သို့မဟုတ် Class နေရာတစ်ခုကို အချိန်တူနှစ်ခါ Booking မလုပ်ရပါ။

PT ရောင်းချတဲ့အခါ —

1. Reception က PT Sale စာရင်းတင်မယ်
2. Manager/Owner က စစ်ပြီး Approve လုပ်မယ်
3. Payment နဲ့ Receipt ထွက်မယ်
4. Trainer ကော်မရှင်ကို System က ရာခိုင်နှုန်းအတိုင်းတွက်မယ်
5. ကျန်ငွေကို Gym ဝေစုအဖြစ် သတ်မှတ်မယ်

ဥပမာ PT Fee 100,000 နဲ့ Trainer ကော်မရှင် 60% ဆိုရင် —

- Trainer ကော်မရှင် = 60,000
- Gym ဝေစု = 40,000

## ဖျော်ရည်နဲ့ Fitness ပစ္စည်း ရောင်းချပုံ

Gym တစ်ဆိုင်ချင်းစီမှာ Product Catalog နဲ့ Stock ကို သီးခြားထားပါမယ်။ Item တစ်ခုမှာ SKU/Barcode၊ အမည်၊ အမျိုးအစား၊ ဝယ်ဈေး၊ ရောင်းဈေး၊ လက်ကျန်နဲ့ လက်ကျန်နည်းသတိပေးအမှတ် ရှိပါမယ်။

- Stock ဝယ်သွင်း၊ ရောင်းထုတ်၊ Return၊ ပျက်စီး/ပျောက်ဆုံး Adjustment အားလုံးကို အကြောင်းရင်းနဲ့ မှတ်တမ်းတင်မယ်
- Sale တစ်ခုမှာ Item တစ်မျိုးထက်ပိုပါနိုင်ပြီး အရေအတွက်၊ ရောင်းဈေး snapshot နဲ့ ကုန်ကျစရိတ် snapshot ကို သိမ်းမယ်
- Payment Approve/Post ပြီးမှ Sale နဲ့ Stock အတည်ဖြစ်မယ်
- Stock ကို သုညအောက်မကျစေရဘဲ တစ်ပြိုင်နက်ရောင်းချမှုကို Server က ထိန်းမယ်
- Item အလိုက် ရောင်းရသည့်အရေအတွက်၊ Revenue နဲ့ Gross Profit ကို Report မှာကြည့်နိုင်မယ်

`Gross Profit = Product Revenue - ရောင်းပြီးပစ္စည်း၏ Cost` ဖြစ်ပြီး Rent၊ Salary စတဲ့ အခြားကုန်ကျစရိတ်မနုတ်ရသေးပါ။ Owner Dashboard မှာ Product source အပြင် Top-selling/Top-gross-profit Item ကို သီးခြားပြရပါမယ်။

## ဝန်ထမ်းလစာ မှတ်ပုံတင်ပုံ

လစဉ်လစာကာလတစ်ခု ဖွင့်ပြီး ဝန်ထမ်းတစ်ယောက်ချင်း ပေးမည့်ငွေကို ထည့်မယ်။

- Fixed amount ကို System က အလိုအလျောက်မသတ်မှတ်ပါ
- လတိုင်း ပေးမည့်ငွေကို စာရင်းရေးရပါမယ်
- Manager/Owner Approve လုပ်မှ လစာ Expense ဖြစ်မယ်
- ငွေသားပေးရင် Cash Book ထဲက နုတ်မယ်
- Reject လုပ်ရင် ကုန်ကျစရိတ်ထဲ မပါပါ

## နေ့အဆုံး ငွေစာရင်းပိတ်ပုံ

နေ့ကုန်ရင် Reception က မိမိကိုယ်တိုင်ဖွင့်ထားတဲ့ Session ကိုသာ၊ Accountant က မိမိ Permission အတိုင်း —

1. Pending စာရင်းတွေ ကျန်သေးလားစစ်မယ်
2. ဒီနေ့အတည်ပြုပြီးသား ဝင်ငွေ/ကုန်ကျစရိတ်ကို ကြည့်မယ်
3. ကောင်တာမှာရှိတဲ့ ငွေသားကို ရေတွက်မယ်
4. System ထဲမှာ တကယ်ရေတွက်ရတဲ့ငွေကို ထည့်မယ်

System က အောက်ပါအတိုင်းတွက်မယ် —

```text
ပိတ်ချိန်ရှိသင့်သောငွေ
= စတင်ငွေ
+ ငွေသားဝင်ငွေ
- ငွေသားကုန်ကျစရိတ်
+ လက်ဖြင့်ပြင်ဆင်ထားသောငွေ
```

တကယ်ရေတွက်တဲ့ငွေနဲ့ မကိုက်ရင် အကြောင်းရင်းရေးရပါမယ်။ ပိတ်ပြီးသား Cash Session ကို ပြန်ပြင်လို့မရပါ။

ရှိသင့်တဲ့ငွေ၊ စုစုပေါင်းဝင်/ထွက်နဲ့ ကွာဟချက်ကို Browser က ပို့တဲ့ပမာဏအဖြစ် မယုံပါ။ Server က အတည်ပြုပြီးသား မပြောင်းလဲနိုင်သော Cash Transaction တွေကနေ ပြန်တွက်ပြီး Session ကို တစ်ကြိမ်တည်းပိတ်ပါတယ်။ Reception က Adjustment အသစ်ရေးပြီး ငွေညှိခွင့်မရှိပါ။

Phase 4 Increment 2 မှာ ဒီဖွင့်ခြင်း၊ လက်ဖြင့်ပြင်ဆင်ခြင်း၊ ပြန်တွက်ပိတ်ခြင်းကို server API က လုပ်ပါတယ်။ Browser စာမျက်နှာကို Increment 9 မှ ထည့်ပါမယ်။ Cash Transaction ကို ပြင်ခြင်း၊ ဖျက်ခြင်း မရှိပါ။ Register code သည် စာလုံးအကြီး `[A-Z0-9_-]` သာဖြစ်ပြီး သီးခြား register စာရင်းမရှိပါ။ Reception role ကိုင်ထားသူသည် နောက်ထပ် role တစ်ခုခု ထပ်ရှိလည်း မိမိဖွင့်ထားသော session ကိုသာ ကြည့်၊ သုံး၊ ပိတ်နိုင်သည်။ လက်ဖြင့်ပြင်ဆင်ခွင့် မရှိပါ။ တစ်ခြား Reception ၏ session ကို မရှိသကဲ့သို့ `404` ပြသည်။ Owner က သတ်မှတ်နိုင်သော စည်းမျဉ်း မရှိသေးခင် လက်ဖြင့်ပြင်ဆင်ခြင်းကို protected Owner role ကသာ လုပ်နိုင်သည်။ Manager၊ Accountant နှင့် custom role ကို `403 PERMISSION_DENIED` ပြသည်။ `mutate()` သည် business transaction ထဲမှာ membership၊ gym၊ finance entitlement နှင့် permission ကို ပြန်စစ်ပြီး session ကို lock ပြီးမှ ထိုအခွင့်အာဏာကို ထပ်စစ်သည်။ ငြင်းပယ်လျှင် ရလဒ်မကျန်ဘဲ idempotency claim ကို မသိမ်းပါ။ Session ကို အရင် lock ပြီးမှ movement ကို ရေးသဖြင့် ပိတ်ပြီးမှ ရွေ့လျားမှု အသစ်မကျန်ပါ။

### အဓိက Card ၄ ခု

1. **Revenue Sources** — New Member၊ Renewal၊ PT၊ Class၊ Product နဲ့ Other တို့ရဲ့ အတည်ပြုပြီးသား အသားတင်ဝင်ငွေကို အများဆုံးမှ အနည်းဆုံး စီပြမယ်။ Product Item အမြတ်နှိုင်းယှဉ်မှုကို ကုန်ကျစရိတ် snapshot ပါတဲ့ Gross Profit နဲ့ သီးခြားစီမယ်။
2. **Pending Payments** — သက်တမ်းလွန်ပြီး `UNPAID` သို့မဟုတ် `PARTIAL` ဖြစ်နေတဲ့ Membership/Class/PT ကြွေးကျန် Member အရေအတွက်နဲ့ ကျန်ငွေစုစုပေါင်းကို ပြမယ်။ Approve လုပ်ရန်စောင့်နေသော Draft တွေကို သီးခြား `Pending Approvals` အဖြစ်ပြမယ်။
3. **Expiring Members** — Gym ရဲ့ local date အရ ၃၊ ၇၊ ၃၀ ရက်အတွင်း သက်တမ်းကုန်မည့် Active Member အရေအတွက်ကို ကြည့်နိုင်မယ်။
4. **Attendance** — ဒီနေ့ Check-in လုပ်ခဲ့တဲ့ Unique Member အရေအတွက်၊ Check-in စုစုပေါင်းနဲ့ Check-out မလုပ်ရသေးဘဲ Gym ထဲရှိနေသူအရေအတွက်ကို သီးခြားပြမယ်။

### Member အခြေအနေ

- Active Members
- New Members
- Expired Memberships
- ဒီနေ့လာသော Unique Members၊ Check-ins နဲ့ လက်ရှိ Gym ထဲရှိသူ
- Approve လုပ်ရန်ကျန်နေသောစာရင်း

### ငွေစာရင်း

- Membership ဝင်ငွေ
- New Member နဲ့ Renewal ဝင်ငွေ သီးခြား
- PT ဝင်ငွေ
- Class ဝင်ငွေ
- Product ရောင်းရငွေ၊ ရောင်းရသည့်အရေအတွက်နဲ့ Gross Profit
- အခြားဝင်ငွေ
- စုစုပေါင်းဝင်ငွေ
- အမျိုးအစားအလိုက် ကုန်ကျစရိတ်
- ဝန်ထမ်းလစာ
- PT ကော်မရှင်
- စုစုပေါင်းကုန်ကျစရိတ်
- အသားတင်အမြတ်

```text
အသားတင်အမြတ် = စုစုပေါင်းဝင်ငွေ - စုစုပေါင်းကုန်ကျစရိတ်
```

Approve မလုပ်ရသေးသောစာရင်းနဲ့ Reject လုပ်ထားသောစာရင်းတွေကို ဝင်ငွေ/ကုန်ကျစရိတ်/အမြတ်ထဲ မထည့်ပါ။

## အရေးကြီးတဲ့ လုံခြုံရေးစည်းမျဉ်းများ

- Reception/Accountant က မိမိတင်ထားသော ငွေစာရင်းကို ကိုယ်တိုင် Approve မလုပ်ရပါ
- Reception က မိမိဖွင့်ထားသော Cash Session ကိုသာ အသုံးပြု/ပိတ်နိုင်ပြီး အခြား Reception Session၊ အခြား Gym Session နဲ့ Manual Adjustment ကို မလုပ်ရပါ
- အတည်ပြုပြီးသား ငွေစာရင်းကို ဖျက်/ပြင်လို့မရပါ
- မှားရင် Void၊ Refund သို့မဟုတ် ပြန်လှန်စာရင်းအသစ်နဲ့ ပြင်ရပါမယ်
- Receipt နံပါတ်ကို ပြန်သုံးလို့မရပါ
- QR ထဲမှာ Member အမည်နဲ့ ဖုန်းနံပါတ် မထည့်ပါ
- Member App က မိမိအချက်အလက်ကိုသာ မြင်ရပါမယ်

## System ကို ဘယ်မှာထားမလဲ

Web Login ကို Next.js BFF က တစ်ဆင့်ခံပေးမယ်။ Browser JavaScript က JWT/Refresh Token ကို မရသလို `localStorage`/`sessionStorage` ထဲလည်း မသိမ်းပါ။ Token ကို `HttpOnly`, Gym host တစ်ခုတည်းအတွက် Cookie နဲ့ထားပြီး localhost သီးခြားစမ်းသပ်မှုကလွဲရင် `Secure`, `SameSite=Lax` သတ်မှတ်မယ်။ Gym အများရှိတဲ့ Account ဆိုရင် Django က ၅ မိနစ်သက်တမ်းရှိတဲ့ တစ်ကြိမ်သုံး Ticket ထုတ်မယ်။ Ticket စာသားကို Browser က မမြင်ရဘဲ BFF Cookie ထဲမှာပဲထားမယ်။ မျက်နှာပြင်မှာ ရွေးစရာ Gym နာမည်တွေပဲပြမယ်။ ရွေးပြီးမှ Session ထွက်မယ်။ Cookie ပြောင်းစေတဲ့ Login/Refresh/Gym ရွေး/Logout အားလုံးမှာ CSRF Header နဲ့ Origin/Referer ကို စစ်မယ်။ Access Token ရည်မှန်းသက်တမ်းက ၁၀ မိနစ်ဖြစ်ပြီး သက်တမ်းကုန်မှုအတွက် Refresh တစ်ကြိမ်၊ မူလ Request ပြန်ပို့မှုတစ်ကြိမ်သာလုပ်မယ်။ Django က Session/Token ကို အဓိကဆုံးဖြတ်ပြီး Refresh Token ပြန်သုံးမိရင် မိသားစုတစ်စုလုံးပိတ်မယ်။ Logout မှာ Django က အာဏာပိုင်အဖြစ် Session ပိတ်ပြီး BFF က Cookie တွေရှင်းမယ်။

JWT အမည်သတ်မှတ်ချက်တွေက Secret မဟုတ်ဘဲ Config ပြောင်းလဲသတ်မှတ်နိုင်တဲ့ တည်ငြိမ်တန်ဖိုးတွေဖြစ်ပါတယ် — issuer `gym-platform-api`, Staff/Web audience `gym-platform`, Member audience `gym-platform-member`။

စတင်အသုံးပြုချိန်မှာ လစဉ် **US$80 ခန့် Budget** နဲ့ VPS Server တစ်လုံးပေါ်မှာ ထားမယ်။

- Web၊ API၊ Database နဲ့ File Storage ကို Docker ဖြင့်ခွဲထားမယ်
- Database နဲ့ File Storage ကို Internet သို့ တိုက်ရိုက်မဖွင့်ပါ
- Backup ကို ထို Server တစ်လုံးထဲမှာပဲ မထားဘဲ အပြင် Storage သို့ ကူးထားမယ်
- သုံးလတစ်ကြိမ် Backup ကနေ ပြန်တင်နိုင်မနိုင် စမ်းသပ်မယ်

VPS တစ်လုံးပျက်ရင် System ခဏရပ်နိုင်ပါတယ်။ ဒါကြောင့် Backup နဲ့ ပြန်တင်နည်းကို ကြိုတင်ပြင်ဆင်ထားရပါမယ်။ Gym နဲ့ အသုံးပြုသူများလာရင် Database ကို သီးခြား Server သို့ ရွှေ့ပြီး System ကို တိုးချဲ့နိုင်ပါတယ်။

တည်ဆောက်ချိန် Version တွေကို Python 3.14.7, Django 5.2.17 LTS, DRF 3.18.0, Node.js 24.20.0 LTS, Next.js 16.4.1 Active LTS, PostgreSQL 18.6 နဲ့ TypeScript 7.0.2 အဖြစ် တိတိကျကျ Pin လုပ်မယ်။ Next.js 16.4.1 သည် အတည်ပြုထားသော လုံခြုံရေးကိုက်ညီမှုပြင်ဆင်ချက်ဖြစ်သည်။ `docs/DEVELOPMENT_PLAN.md` သည် မပြောင်းလဲရသော သမိုင်း baseline အဖြစ် Next.js 16.3.3 ကို ဆက်လက်မှတ်တမ်းတင်ထားသည်။ Django/DRF ကို Python နဲ့၊ Next.js/TypeScript ကို Node နဲ့၊ Database Migration/RLS ကို PostgreSQL အစစ်နဲ့ စမ်းသပ်ပြီး ကိုက်ညီမှုကို အတည်ပြုမယ်။

## အတိုချုပ်

Member တစ်ယောက်လာရင် —

```text
Member ရှာ/အသစ်ဖွင့်
    → Membership သက်တမ်းစစ်
    → Payment ကို Manager/Owner အတည်ပြု
    → Check-in
    → Train
    → Check-out
    → နေ့အဆုံး Cash Book ပိတ်
```

Reception က အချက်အလက်ထည့်ပေးပါတယ်။ ငွေပမာဏ၊ သက်တမ်း၊ ဝင်ခွင့်နဲ့ အမြတ်ကို System ကတွက်ပေးပြီး Manager/Owner က ငွေစာရင်းကို သီးခြားစစ်ဆေးအတည်ပြုပါတယ်။

Browser Login ဆုံးဖြတ်ချက်ကို [ADR 0002](./adr/0002-nextjs-bff-browser-authentication.md)၊ Reception Cash Session အခွင့်အာဏာကို [ADR 0003](./adr/0003-reception-cash-session-authority.md) မှာ မှတ်တမ်းတင်ထားပါတယ်။ MFA သည် TOTP ဖြစ်ပြီး Platform Admin နှင့် Owner အတွက် မဖြစ်မနေ လိုအပ်သည်။ ကာကွယ်ထားသော Owner လုပ်ဆောင်ချက်များအတွက် မကြာသေးမီက MFA အတည်ပြုချက် လိုအပ်သည်။ လျှို့ဝှက်ချက်များကို ကုဒ်ဝှက်သိမ်းပြီး code ပြန်သုံးခြင်းကို ကာကွယ်သည်။ ပိုကျယ်သော role-based MFA ကို နောက်မှ ဆုံးဖြတ်နိုင်သည်။ Email ပို့ခြင်းသည် Django ၏ configurable email backend ဖြစ်သည်။ Test နှင့် E2E တွင် မပို့သော backend ကို သုံးသည်။ ဖိတ်ကြားချက်၊ စကားဝှက် ပြန်လည်ရယူခြင်း၊ သို့မဟုတ် Phase 2 သက်တမ်းကုန် email ကို production-ready ဟု မသတ်မှတ်မီ အတည်ပြုထားသော transactional provider ကို ပြင်ဆင်ရမည်။ Vendor ရွေးချယ်မှုနှင့် deployment ပြင်ဆင်ချက်ကို ရွှေ့ဆိုင်းထားသည်။ Jurisdiction ကို Production မတိုင်မီ ဆုံးဖြတ်ရမည်။ Phase 3 check-in device ပုံစံကို ADR 0007 နှင့် ADR 0008 အရ အကောင်အထည်ဖော်ပြီးဖြစ်သည်။ Vendor-specific adapter မပါပါ။ Expo/Bare React Native ရွေးချယ်မှုကို Phase 7 မှာ ဆုံးဖြတ်ရမည်။
